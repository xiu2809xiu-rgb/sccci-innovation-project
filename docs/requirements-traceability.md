# Requirements traceability

This matrix links every module requirement (M1 to M6, [CLAUDE.md](../CLAUDE.md) section 2) and every product capability (A to G, CLAUDE.md section 4) to four things: the feature or control that meets it, where that lives in the code, the evidence an assessor can check, and the area that owns it. Every feature maps to at least one requirement. A feature that maps to none does not belong in the product.

## How to read and maintain it

| Column             | Meaning                                                                                                                                                                                                                     |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ID                 | Stable row id, `<requirement>-<nn>` (for example `M4.1-06`). An id is never renumbered or reused. A row that is no longer needed stays in the table, with the reason and an ADR link in its feature text.                   |
| Feature or control | What meets the requirement                                                                                                                                                                                                  |
| Code location      | Where it lives. Paths follow the planned layout ([CLAUDE.md](../CLAUDE.md) section 6, [module ownership](team/module-ownership.md)) and are replaced with real paths when the code lands. Paths that exist today are links. |
| Evidence           | What proves it: a test file, a screenshot in `docs/design/screenshots/`, a metric (CI report, Lighthouse, `/metrics`), or a document                                                                                        |
| Owner              | Ownership area 1 to 4 ([module ownership](team/module-ownership.md)), or "All" for group deliverables and team practice                                                                                                     |
| Status             | **Planned**: not started. **In progress**: partly built or in an open PR, with incomplete evidence. **Done**: the evidence exists in the repository and has been verified, by passing CI or by review for documents.        |

**Update rule.** Every PR updates the rows it affects; this is part of the definition of done (CLAUDE.md section 11). The PR template (Phase 2) asks for the row ids, and reviewers check that the evidence links resolve. Rows completed on the `feat/platform-base` branch were verified on that branch before its PR.

**Evidence conventions.** These follow the NestJS 12 + Vitest defaults, confirmed in Phases 2 and 3:

- **Unit tests:** `*.spec.ts` next to the code they test.
- **API integration tests:** Vitest + Supertest against a real PostgreSQL and Redis, in `apps/api/test/<module>.int-spec.ts`.
- **Browser end-to-end tests:** Playwright + axe, in `apps/web/e2e/`.
- **Coverage:** `@vitest/coverage-v8` (`pnpm --filter @huitong/api test:cov`); the CI coverage report arrives with the area 1 domain logic (M4.3-01).

**M3 and the product's AI.** M3 is about _how we build_: using AI coding tools (AWS Kiro as the IDE) responsibly. The product's own AI features (capability E) map to M1, M2 and M6.4, not to M3.
