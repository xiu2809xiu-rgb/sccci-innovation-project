# Area 4: Governance, security and monitoring

This guide is the starting point for area 4's owner, Angelyn. It explains what is already in the repository, what is yours to build, the design we recommend, a build plan by sprint, the risks, and how the area plugs into the rest of HuiTong. Area 4 covers capabilities F and G in [CLAUDE.md](../../CLAUDE.md) section 4, for Problem Statement #5 ([ADR 0023](../adr/0023-retarget-ps5-aspri-ipi.md)): the policy that decides who may see what is administered, audited and visible; ASPRI-IPI is ready when an agency checks a result; trainees' data is classified, kept only as long as needed and shared with each agency only as far as its allowlist goes; the system is observable; its use is measured with consent; every AI call is costed; and the demo runs on AWS.

The ground rule is in [module ownership](module-ownership.md#ground-rules): the core logic is yours to write. For area 4 that is the administration of the policy and the registers (each agency's allowlist among them), audit readiness, the retention purge, OpenTelemetry tracing and metrics, the clickstream and AI usage aggregations with budgets and alerts, and the AWS deployment. Whether the head start below is reworked for #5 by the team lead or by you is your call, relayed through the team lead (step 6 of [prompt 005](../ai/prompts/005-retarget-ps5-aspri-ipi.md)).

## The recommended design

```mermaid
flowchart LR
  ADMIN["Governance pages<br/>(administration)"] --> SVC["GovernanceService<br/>one command per change"]
  SVC --> TX[("one transaction:<br/>the change and its audit event")]
  TX --> RELOAD["AccessPolicyService.reload()<br/>on every API instance"]
  RELOAD --> GUARD["RBAC guard, FieldMasker,<br/>each agency's allowlist (area 1)"]
  JOB["Retention purge job<br/>a Strategy per action"] --> TX
  AUDIT[("audit_events")] --> EVID["A run's evidence<br/>for an agency's check (F-8)"]
  API["API requests, queue jobs,<br/>connector calls"] --> OTEL["OpenTelemetry traces"]
  API --> PROM["prom-client /metrics"]
  OTEL --> CW["CloudWatch logs, metrics, alarms"]
  PROM --> CW
  USAGE[("ai_usage_records")] --> AGG["Dashboard aggregations<br/>replace the sample repository"]
  CLICKS[("clickstream_events")] --> AGG
  PROM --> AGG
  AGG --> DASH["Analytics pages"]
```

**Patterns** (add each to [patterns.md](../architecture/patterns.md) as you build it):

| Pattern                | Where it earns its place                                                                                                                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Command with its audit | Each administration change is one service method: validate, write, and record the audit event with the before and after state and the reason, in one transaction (`AuditLogService.record(input, meta, tx)`), then reload the policy |
| Observer               | API instances each cache the policy. On ECS there are several, so publish a `policy.changed` event that every instance answers with `reload()`; the in-process `DomainEventBus` covers one instance only, so this needs Redis        |
| Strategy               | One retention action per kind (delete, anonymise, archive), chosen by each rule; one aggregation per dashboard                                                                                                                       |
| Repository             | Replace `MockAnalyticsDashboardsRepository` with aggregations bound to the same abstract class; give `GovernanceRepository` its writes. The controllers and the contract do not change                                               |
| Interceptor            | One NestJS interceptor records each request's duration and outcome as a prom-client histogram, labelled by route pattern and status, never by user or URL                                                                            |

**An allowlist change.**

```mermaid
sequenceDiagram
  participant D as Data protection officer (through an administrator)
  participant S as GovernanceService
  participant DB as PostgreSQL
  participant P as AccessPolicyService
  D->>S: PUT the agency's entry (fields, purpose, status ACTIVE, reason)
  S->>DB: in one transaction: update the entry (version + 1) and append the audit event
  S->>P: reload(), and publish policy.changed for the other instances
  P-->>D: the entry; the agency's next submission follows it
```

**Rules to keep.**

- **The audit log only grows.** No endpoint updates or deletes an event, and the viewer names the fields an event changed, never their values. Archiving old segments records the last archived hash, so the chain still verifies ([GRS 2.4](../grs/grs-by-design.md#24-audit)).
- **Default deny per agency, in the viewer too.** An agency receives only what an ACTIVE entry shares ([A-81](../assumptions.md)), and an `access.fields_withheld` event names the fields and the entry versions, never the values.
- **Separation of duties.** A system administrator configures the platform but cannot approve rules, verify results or submit; an assessor cannot verify ([GRS section 2.1](../grs/grs-by-design.md#21-roles-and-responsibilities)). Refuse any change that breaks these, and any change that leaves no role with `governance:manage`.
- **Every change has a reason and a version.** An allowlist entry's version goes up with every change to it (fields, purpose, status or approver); every change records who made it and why.
- **Monitoring never identifies people.** Metric labels and trace attributes carry route patterns, status codes and connector ids, never user ids, emails or trainee IDs. Clickstream stays anonymous: no consent or Global Privacy Control, no event ([ADR 0016](../adr/0016-observability-baseline.md)).
- **Costs are estimates.** The AI usage dashboard prices tokens at the reference prices (A-52), and says so.

**Decisions that are yours** (record each in an ADR or an assumption when you make it):

- **Each agency's entry.** Which fields MOM, SSG/WSDA and ITE each need, and who approves an entry (the DPO, [A-79](../assumptions.md)), are open until the client answers [Q-66](../client/questions-for-client.md), [Q-67](../client/questions-for-client.md) and [Q-69](../client/questions-for-client.md), with [Q-40](../client/questions-for-client.md) for who approves. Until then, seed each agency with the smallest set its assumed format needs.
- **Retention.** How long assessment records, submissions and the audit log are kept, which the client sets ([A-80](../assumptions.md), [Q-79](../client/questions-for-client.md)); what "anonymise" removes for each kind; how the audit log is archived; and how often the purge runs.
- **Day boundaries.** The dashboards count whole UTC days ([`dashboard-window.ts`](../../apps/api/src/modules/analytics/dashboards/dashboard-window.ts)). ASPRI-IPI works in UTC+8, so Asia/Singapore days may read better.
- **The infrastructure-as-code tool** for `infra/aws` (Terraform, the AWS CDK or CloudFormation), recorded in its own ADR ([ADR 0014](../adr/0014-deployment-docker-aws.md)), and ECS Fargate or App Runner for the demo.
- **Local dashboards.** Grafana with Prometheus, or the in-app observability page alone ([ADR 0016](../adr/0016-observability-baseline.md)).
- **Budgets and alerts.** A monthly budget per feature, the threshold for a warning, and where it goes (CloudWatch, email or in-app).

## Step-by-step build plan

1. **Access administration (F-1, sprint 8).** Check the six #5 roles' baseline matrix and clearances, which area 1 adds with the roles, against GRS section 2.1; then endpoints to change them, each a command with its audit and a policy reload, and the edit mode on the access page. Start with the `governance:manage` refusal and F-1's #5 refusals (approving rules, verifying, submitting) in [`governance-administration.spec.ts`](../../apps/api/src/modules/governance/governance-administration.spec.ts), rewording its earlier-statement cases as you go.
2. **The audit viewer (F-2, sprint 9).** A result's trail from capture to submission; name the fields an `access.fields_withheld` event withheld (they are in its metadata); a CSV export that is itself audited; and a scheduled chain check that alerts when the chain breaks.
3. **Classification (F-3, sprint 9).** The trainee and result fields with their levels and reasons; a changed level is audited, and a field an allowlist entry depends on cannot be lowered without review.
4. **Each agency's allowlist (F-7, sprint 10).** Implement the status change behind the transfers page (`GovernanceService.changeTransferStatus`) for agency entries, rename the page for #5, and add the `policy.changed` event for the other instances. Area 1 enforces the entries in every submission (B-9).
5. **Retention and audit readiness (F-5 and F-8, sprint 11).** A purge job with one strategy per action, its queue added to [`queue-names.ts`](../../apps/api/src/infrastructure/queues/queue-names.ts) in a small pull request of its own, `lastAppliedAt` recorded and each run audited; then a run's evidence in one view for an agency's check.
6. **The security checklist and the PDPA search (F-6 and F-9, sprint 12).** `docs/grs/security-checklist.md` with the team: each OWASP Top 10 and API Security Top 10 category, its control, the code and the test or scan that proves it. Then the search for everything HuiTong holds about a trainee, audited.
7. **Traces and metrics (G-1, sprint 14).** The telemetry bootstrap (a shared file: area 1 reviews it), traces across API requests, BullMQ jobs and connector calls, the trace id as the error envelope's `traceId`, and `/metrics`. Then an observability repository that reads them, replacing the sample.
8. **Clickstream (G-2, sprint 15).** Page statistics and the funnel from `clickstream_events` (order each session's page views by time), sessions by language, and the 13-month retention of raw events.
9. **AI usage (G-3, sprint 16).** Aggregations over `ai_usage_records` by feature, person, model and day, with the median latency, then budgets and alerts. Bind the real repository in [`AnalyticsModule`](../../apps/api/src/modules/analytics/analytics.module.ts), remove `@ServesMockData()` and delete the sample: the badge disappears by itself.
10. **AWS (G-4 and G-5, sprint 17).** The deployment in ADR 0014, documented in `infra/aws/`, with CloudWatch alarms and the ZAP baseline. Area 4's backup takes part in one rehearsal ([module ownership](module-ownership.md#backup-owners)).
11. **Switch on your end-to-end steps** in the hero journey's specs in the pull request that makes each pass.

## The risks

| Risk                                                   | Mitigation                                                                                                   |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| An agency receives a field it does not need            | Default deny; each entry names its purpose and approver; E2E #3 and an audit of every withholding (GRS R-23) |
| A policy change locks everyone out of administration   | Refuse a change that leaves no role with `governance:manage`; a test for it                                  |
| API instances disagree about the policy after a change | `policy.changed` through Redis, and a test with two application instances                                    |
| The audit trail cannot answer an agency's check        | A run's evidence in one view, each item linked to its audit events (GRS R-14)                                |
| The chain check slows down as the log grows            | Verify from a stored checkpoint (the last archived hash); the endpoint is rate-limited already               |
| Metrics or traces leak personal data                   | An allowlist of labels and attributes, and a test that inspects `/metrics`                                   |
| Small numbers in the clickstream point to one person   | No user ids are stored; show page counts only above a minimum number of sessions                             |
| AI costs surprise the team                             | Budgets with alerts; the reference prices reviewed when the provider changes                                 |
| The AWS setup is known by one person, or costs run on  | The backup's rehearsal; the demo scaled down outside demo windows (ADR 0014)                                 |
| Sample data mistaken for the working product           | `@ServesMockData()` and the "Sample data" badge until the real repositories are bound                        |
