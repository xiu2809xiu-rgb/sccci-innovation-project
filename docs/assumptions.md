# Assumptions register

HuiTong 汇通 · ASPRI-IPI · Problem Statement #5 (the team's first choice) · v0.3, 24 Oct 2026 (W1)

- **Requirement:** M1 design thinking (traceability row M1-08); also supports M2 (GRS by design).
- **Status:** written before the briefing call (the week of 2 Nov, W3), and retargeted to statement #5 on 24 Oct 2026 ([ADR 0023](adr/0023-retarget-ps5-aspri-ipi.md)). All 43 assumptions are Open: 21 are new, 14 were rewritten for #5 and 8 still hold as they were.
- **Owner:** Richie (team lead) maintains the register; each area owner keeps their own rows current.

What we know about ASPRI-IPI's systems, data, processes and compliance arrangements comes only from the brief ([problem-statement.md](problem-statement.md)). Anything else the design relies on is recorded here as an assumption until the client confirms or corrects it. Each row says why we assume it, what changes if it is wrong, and how and when we will find out: usually through a client question (Q-xx, [client/questions-for-client.md](client/questions-for-client.md)), otherwise at a team checkpoint. Risks (R-xx) refer to the register in [grs/grs-by-design.md](grs/grs-by-design.md#3-risk-register). Module requirements are M1 to M6 and capabilities are A to G ([CLAUDE.md](../CLAUDE.md) sections 2 and 4).

> **Not legal advice.** Compliance rows are design considerations drawn from the public texts of the Singapore PDPA and related guidance. The client's compliance team and its DPO confirm what applies.

## How to use this register

| Column                   | Meaning                                                                                                                                                                             |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ID                       | `A-nn`, stable. Ids are never renumbered or reused; a new assumption takes the next free id (A-85 onwards)                                                                          |
| Category                 | Client systems, data, process, compliance, technical or project (see [Summary](#summary))                                                                                           |
| Assumption               | What we take to be true, stated so that it can be proved wrong                                                                                                                      |
| Rationale                | Why it is a reasonable working assumption today                                                                                                                                     |
| Impact if wrong          | What has to change, naming the affected areas, ADRs and risks (R-xx) so that dependants can be found                                                                                |
| How and when we validate | The client question (Q-xx) or checkpoint that settles it, its deadline and the owner. P1 questions are due before the W5 proposal, P2 before the W8 build, and P3 follow in writing |
| Status                   | Open, Confirmed, Revised or Retired (below)                                                                                                                                         |

| Status    | Meaning                                                                                                                                                   |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Open      | Not yet validated; the design relies on it                                                                                                                |
| Confirmed | Evidence shows it holds; nothing else changes                                                                                                             |
| Revised   | Evidence showed it was wrong or incomplete. The row now states what is true, the old text stays struck through, and dependent documents have been updated |
| Retired   | No longer guides the design: scope changed, or a newer row replaces it (the row names it)                                                                 |

- **Cite by id.** Any document, ADR, mock, schema or test that depends on an assumption names its id, so a repository search for `A-nn` finds everything to revisit.
- **Same pull request.** A change that adds, confirms or breaks an assumption updates this register in the same PR ([team/module-ownership.md](team/module-ownership.md), shared definition of done). Owners update their own rows.
- **One assumption per row.** Split a row rather than widen it, so that each part can be confirmed on its own.
- **Earlier statements.** A-01 to A-63 were written for the earlier statements. The rows that still hold keep their ids; a row rewritten for #5 says so in its status. Their earlier text, and the rows that no longer apply, are in the tag `archive/ps7-lesso-solar`.

## How to retire an assumption

1. **Validate.** Get evidence: the client's answer to the linked question, checked against the corrected minutes; a client artefact (a checklist, a field list, a submission template); a measurement; or, for internal rows, a merged ADR or a passing CI check. Record client answers in the Answer column of [client/questions-for-client.md](client/questions-for-client.md).
2. **Update the status.** Set it to Confirmed, Revised or Retired, with the date and the evidence, for example "Confirmed, 2026-11-02 (Q-68)". For Revised, strike through the old statement and write what is true after it. For Retired, give the reason or the replacing row. Never delete a row or reuse its id; a new working assumption gets a new id. (The retarget to #5 is the one exception: the rows that no longer apply moved to the archive tag, and their ids stay retired.)
3. **Change the documents and ADRs that depend on it.** Search the repository for the id and follow the "Impact if wrong" pointers:
   - **ADRs:** an accepted ADR is never rewritten. Write a superseding ADR ([ADR 0001](adr/0001-record-architecture-decisions.md)) and update the [index](adr/README.md).
   - **Mocks, contracts and mappings:** update the mock service, the zod schemas in `@huitong/shared` and the affected mapping configs (as new versions, through the normal approval).
   - **Design thinking and metrics:** relabel personas, journeys and hypotheses from Assumed to Partly validated or Validated ([design-thinking/README.md](design-thinking/README.md)), and replace baselines in [problem-statement.md](problem-statement.md#26-success-metrics) and [design-thinking/success-metrics.md](design-thinking/success-metrics.md).
   - **GRS and ownership:** re-score the affected risks (R-xx) in [grs/grs-by-design.md](grs/grs-by-design.md), and update the area guides in `docs/team/` if scope or interfaces move.
4. **Update traceability.** In [requirements-traceability.md](requirements-traceability.md), add the evidence to M1-09 (client discovery) and update every row whose feature, code location or evidence changed. Row ids are never renumbered.
5. **Log and review.** Add a line to the change log above in the same pull request, and ask the owner of each affected area to review it.
